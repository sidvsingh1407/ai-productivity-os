# TarkaX Phase 8: Agentic Intelligence Platform Architecture

## Executive Summary
This document outlines the architectural shift for TarkaX from a static report-generating platform to an agentic operational intelligence platform. The primary goal is to transition from "Assessment → Report" to "Assessment → Intelligence → Guidance → Action."

TarkaX will introduce specialized, domain-specific operational intelligence agents. Crucially, these agents operate under a strict **"Deterministic Brain + LLM Interface"** paradigm. Agents do not generate primary truth (scores, findings, risks); they explain, prioritize, and contextualize the primary truth generated by TarkaX's existing deterministic engines.

## 1. Agent Responsibilities
The platform will utilize specialized agents. While the architecture supports all agents, Phase 8 will follow a phased rollout starting with Phase 8A (Audit Agent).

*   **Audit Intelligence Agent (Phase 8A):** Explains assessment results, scores, findings, and recommendations. Answers "Why is my score X?" and "What should I fix first?"
*   **Executive Advisor Agent (Phase 8B):** Provides executive-level decision support, strategic guidance, top priorities, and cross-domain summaries.
*   **Risk Agent (Phase 8C):** Analyzes future-state risks, cost of inaction, and scenario prioritization based on current gaps.
*   **Workflow Intelligence Agent (Future):** Analyzes operational workflows, identifies bottlenecks, and recommends automation priorities.
*   **Governance Agent (Future):** Acts as an operational governance advisor, identifying missing controls and compliance risks.

## 2. Agent Boundaries
To maintain trust, audibility, and system integrity, strict boundaries are enforced:
*   **Agents Do Not Decide Truth:** Agents cannot invent, alter, or negotiate scores, maturity ratings, risk levels, findings, or recommendations.
*   **Agents Explain Truth:** Agents are restricted to explaining, summarizing, prioritizing, and conversing about the deterministic outputs.
*   **Model Agnosticism:** The agent layer must not be tightly coupled to any specific LLM provider (e.g., OpenAI). It must interface via an internal `LLMService` abstraction layer.

## 3. Shared Context Design
Agents must not query the database independently to prevent duplicated logic and inconsistent states. All context is built by a central **`ContextAssembler`**.

*   **ContextAssembler:** A backend service responsible for gathering all necessary data (audit results, workflow results, organization profile, historical assessments, risk projections).
*   **Unified Context Object:** The `ContextAssembler` compiles the gathered data into a single, unified structure (e.g., JSON/Dict containing `organization`, `audit_results`, `recommendations`, `risks`, `history`).
*   **Consumption:** Every agent consumes this identical Unified Context Object to ensure consistent, grounded answers across the platform.

## 4. Orchestrator Design
The system uses a central **`AgentOrchestrator`** to route requests.
*   **Architecture:** The Orchestrator acts as the single entry point. It receives a query, determines the appropriate specialized agent, delegates the task (passing the Unified Context), and optionally combines outputs if multiple domains are queried.
*   **Phased Implementation:** The Orchestrator will be fully architected to support all future agents, but during Phase 8A, it will only route traffic to the `AuditAgent`. This "build the highway, open one lane" approach ensures API stability.

## 5. Memory Architecture
Phase 8 focuses on relational storage to avoid premature complexity.
*   **Storage Mechanism:** PostgreSQL only. Vector databases or graph databases are strictly prohibited until retrieval quality necessitates them.
*   **Data Models:** Memory will be stored in structured relational tables. This includes:
    *   Organization profiles and maturity state.
    *   Conversation history and context.
    *   Agent-generated summaries of interactions.
    *   Historical assessment trends and recurring findings.

## 6. API Architecture
The API strictly enforces that context injection occurs securely on the backend, never trusting the frontend for state.

**Data Flow:**
1.  **Frontend:** Sends user question and minimal identifiers (e.g., `{ "question": "Why is governance weak?", "audit_id": "123" }`).
2.  **API Layer:** Authenticates request and validates permissions.
3.  **AgentOrchestrator:** Receives request.
4.  **ContextAssembler:** Looks up the organization, pulls the latest deterministic audit results, findings, and risks from the database, and builds the Unified Context.
5.  **Agent Routing:** Orchestrator passes the question and the Unified Context to the specific Agent (e.g., `AuditAgent`).
6.  **LLM Service:** The Agent constructs the prompt using the context and calls the provider-agnostic `LLMService`.
7.  **Response:** The explained, prioritized guidance is returned to the frontend.

## 7. UI Architecture
The UI will integrate intelligence naturally rather than introducing a disconnected generic chat interface.
*   **Embedded Experiences:** Intelligence features will exist as contextual actions within current reports and dashboards (e.g., "Explain This Finding" buttons, "Ask TarkaX" side panels).
*   **No Dedicated Workspace (Phase 8A):** A standalone "Operational Intelligence Workspace" will be deferred until usage patterns justify a dedicated route.
*   **Focus:** The interface must drive users toward understanding *what action to take next*, not just engaging in chat.

## 8. Risks
*   **Hallucination of Truth:** The highest risk is the LLM fabricating a score or recommendation not present in the deterministic engine. Mitigation: The `ContextAssembler` strict boundaries, explicit prompt engineering constraining the LLM to the provided context, and the "Deterministic Brain" rule.
*   **Premature Optimization:** Introducing complex vector DBs or generic agent frameworks (Langchain/LlamaIndex) could bloat the system. Mitigation: Stick to Postgres and custom, lightweight Orchestrator/Agent classes initially.
*   **Provider Lock-in:** Tying prompts and logic directly to OpenAI APIs. Mitigation: The `LLMService` abstraction layer.
